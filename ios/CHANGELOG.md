# 변경 기록

## 1.0.9 · 답장·번역 알림 개별 설정

- 두 알림을 모두 켜면 답장 도착과 서버 번역 완료 때 각각 한 번씩 알립니다. 하나만 켜면 해당 알림만 보냅니다. `다른 화면을 볼 때만` 조건은 각 완료 시점에 적용합니다.
- 기존 서버가 붙이는 번역 대기 표식이 답장 알림을 막지 않습니다. 이전 번역 실패·생략 시의 예비 답장 알림은 추가 발송하지 않아 중복을 막습니다.
- iOS/AND 확장과 서버 플러그인을 함께 업데이트하고 서버 재시작 → 실리 페이지 새로고침을 적용합니다. 브랜치는 기존 `ios`를 유지합니다. 알림 웹앱 재설치·기기 재연결은 필요 없습니다. 릴레이·번역 서버는 이번 변경으로 추가 업데이트하지 않습니다.
- iOS/AND 자동 검사 합계 114개 통과. 전송 실패·번역 실패·번역 생략 시 생성/번역 재실행 없이 알림만 처리하는 Verba Server 연동 검사 8개를 포함합니다. 실제 푸시는 모의합니다.
- 알림 전송 실패가 답장 생성이나 번역을 다시 실행하지 않습니다. 실제 Apple/Google 푸시 수신·도착 순서는 기기와 네트워크에서 별도 확인해야 합니다.

## 확장·서버 1.0.7 · 2026-10-23

- 브라우저가 화면 상태 전송의 keepalive 요청을 거절하면 같은 상태·시각으로 일반 요청을 한 번 재시도합니다. 앱을 나갔는데 서버에는 화면을 보고 있는 것으로 남아 알림이 생략될 수 있는 경로를 보완했습니다.
- 상태 전송이 최종 실패하거나 서버가 오류를 반환하면 설정창에 실패를 표시합니다. 무제한 재시도하거나 알림 조건을 우회하지 않습니다.
- 기존 `ios-preview` 설치 경로에도 같은 iOS 코드를 반영합니다. 알림 웹앱과 AND 웹앱 파일은 유지합니다.
- 알림과 복구는 독립적으로 처리됩니다. 알림은 첫 정상 답장 수신을 뜻하며, 검수 완료·채팅 저장·자동 복구 성공을 보장하지 않습니다. 검수 미완료 복구의 보류 조건은 변경하지 않았습니다.
- 상태 전송 실패를 자동 검사에서 재현하고 수정 후 검증했습니다. 릴레이 연동 검사는 Apple 푸시를 모의하며 실제 아이폰 수신 확인은 별도로 필요합니다.

## 확장·서버 1.0.6 · 2026-10-11

- 서버가 **첫 정상 답장 본문을 수신하면 한 번** 알립니다. 또또·100LOG의 검수 완료나 화면 표시를 기다리지 않으므로 알림 후에도 검수·재작성이 진행 중일 수 있습니다. 빈 응답·오류·생각만 있는 응답과 기억 수집·검수 등 보조 요청은 제외하며, 같은 생성 과정의 재시도·재작성 알림은 중복으로 보내지 않습니다.
- 이전 버전 확장의 검수 대기 표시도 새 서버에서는 정상 답장 수신 시 처리합니다. 기존 검수 완료 통지는 추가 알림을 만들지 않습니다.
- 검수 실행 위치와 또또·100LOG·릴레이 코드는 변경하지 않습니다. 이번 변경 때문에 해당 확장들을 추가 업데이트할 필요는 없습니다.
- 실리팝 확장과 서버를 함께 업데이트하고 서버 재시작·실리 페이지 새로고침을 해야 합니다. 알림 웹앱 재설치·기기 재연결은 필요 없습니다.
- 자동 검사로 검증했으며 실제 휴대폰 수신은 별도 확인이 필요합니다. 아래 이전 버전의 검수 완료 대기는 이번 버전에서 해제했습니다.

## 확장·서버 1.0.5 · 2026-10-11

- 또또 1.13.19 이상·100LOG 1.9.32 이상의 검수 연동을 추가했습니다. 검수를 켠 확장이 모두 끝나고 최종 답장이 표시될 때만 알립니다.
- 서버의 실제 정상 답장 수신과 브라우저의 검수 완료 확인을 모두 요구합니다. 초안 수신, 검수·기억 수집 결과, 빈 응답·오류만으로는 검수 완료 알림을 보내지 않습니다.
- 요청 종류가 normal이어도 실제 답장 생성 경로가 확인되지 않은 보조 요청은 알림에서 제외합니다.
- 중복 완료 확인·재작성에 따른 반복 알림을 막고 취소·채팅 전환 시 대기를 해제합니다. APK·iOS·AND를 함께 설치해도 검수 연동을 공유합니다.
- 브라우저가 멈추면 검수와 알림도 재개될 때까지 기다립니다. 진행 중 페이지 새로고침·서버 재시작 시 검수 알림 대기는 복원되지 않습니다.

확장과 서버를 함께 업데이트한 뒤 서버를 재시작하고 실리 페이지를 새로고침해 주세요. 알림 웹앱의 재설치·기기 재연결은 필요하지 않습니다. 자동 검증은 실제 코드를 실행하되 푸시 전달은 모의하며 실기기 수신은 별도 확인입니다.

## 확장·서버 1.0.4 · 2026-10-11

- 종류가 없는 요청은 실제 답장 생성 경로가 확인된 경우에만 알림 대상으로 처리합니다. 검수·기억 수집 등 보조 요청을 답장으로 오인하는 경로를 차단했습니다.
- 화면을 나가거나 페이지가 동결된 뒤 상태 확인이 실행되어도 백그라운드 상태를 유지합니다.
- 빈 문자열·공백·생각 전용 응답·오류 응답은 답장 알림에서 제외합니다.
- 탭마다 별도 식별자를 사용하여 다른 탭의 화면 상태가 알림 판단을 덮어쓰지 않도록 했습니다.
- gzip·deflate·Brotli 압축 응답에서도 실제 답장 내용을 판별합니다.
- 실제 릴레이 서버를 이용해 JSON·스트리밍·헤더 없는 스트리밍, 요청 접수 응답 유실 시 재시도와 중복 방지를 검증했습니다. 푸시 전달은 모의했으며 실기기 수신 확인은 별도입니다.

업데이트 시 설치 명령을 다시 실행하여 확장과 서버를 함께 갱신하고 서버 재시작 및 실리 페이지 새로고침을 합니다. 알림 웹앱은 1.0.3 그대로이며 재설치·기기 재연결은 필요하지 않습니다.

## 1.0.3 · 2026-10-09

- APK와 동일하게 요청 시점의 캐릭터 이름을 기본으로 표시합니다. 이름이 없으면 ‘답장이 도착했어요’로 표시하며 선택 옵션은 두지 않습니다.
- 확장·서버·웹앱을 1.0.3으로 맞췄습니다. 확장·서버 업데이트 후 설치한 알림 앱도 한 번 열어 갱신해 주세요. 기존 구독은 유지됩니다.
- 대화 본문이나 AI 키는 전송하지 않습니다. 캐릭터 이름은 암호화된 푸시에 포함되며 잠금 화면에도 표시될 수 있습니다.
- 이름 수집·전송·서비스 워커 표시 경로는 자동 검사했습니다. 이번 변경은 실제 아이폰 수신을 재확인하지 않았습니다.

## 1.0.2 · 2026-10-08

- 일반 생성 이벤트 순서에 의존하던 알림 표시 조건을 없애고, 실제 전송 직전 요청의 종류로 일반 답장·재생성·스와이프를 판별합니다. 중간에 quiet/dry 생성 이벤트가 끼어 표시가 누락되는 경우를 수정했습니다.
- 최종 채팅 요청 데이터 이벤트에도 알림 표시를 붙입니다. 다른 확장이 미리 보관한 fetch를 사용해도 이 이벤트를 거친 요청에는 표시가 유지됩니다. 기존 fetch/Relay 경로도 유지합니다.
- quiet·사용자 대신 생성·이어쓰기 및 알림 비활성 상태는 제외합니다. 릴레이 재시도의 요청 식별자와 본문은 유지하여 중복 생성을 방지합니다.
- 실제 웹 확장 코드를 실행하는 회귀 테스트에서 이전 버전의 표시 누락을 재현했습니다. 서버와 릴레이 연동도 모의 검증하며 실제 Apple 기기 수신은 별도 확인이 필요합니다.

기존 업데이트 명령으로 설치한 뒤 서버를 재시작하고 **메시지를 보내는 기기의 실리 페이지를 새로고침**하세요. 기기를 다시 연결할 필요는 없습니다.

## 1.0.1 · 2026-10-08

- 응답 Content-Type이 빠진 정상 SSE 스트리밍 답변을 JSON으로 잘못 읽어 실제 답장 알림을 생략하던 문제를 수정했습니다. 본문의 SSE 프레임도 확인하며 오류·생각만 있는 응답에는 알림을 보내지 않습니다.
- 테스트 알림과 실제 답장 결과를 따로 저장하고 확장 설정에 시각과 함께 표시합니다. 연결 확인을 누르면 갱신되며 테스트 성공을 실제 답장 전송 성공으로 오해하지 않도록 했습니다.
- 요청의 알림 표시 누락, HTTP 오류, 응답 판별 실패, 연결 중단, 표시 조건에 따른 생략을 구분합니다. Termux 서버 로그에도 test/reply와 처리 결과를 남기며 채팅 본문·키·구독 주소는 기록하지 않습니다.

서버 플러그인과 웹 확장을 함께 업데이트하는 기존 설치 명령을 다시 실행한 뒤 서버 재시작·실리 페이지 새로고침이 필요합니다. 알림 앱 재설치나 기기 재연결은 필요 없습니다. 진행 중이거나 복구할 답장을 먼저 받은 뒤 재시작하세요.

기존 코드에서 알림 누락을 재현하고 수정 후 회귀 테스트 및 릴레이 1.0.1 연동을 검증했습니다. Apple 푸시 전송은 모의했으므로 실제 아이패드에서의 수신 확인은 별도입니다.
